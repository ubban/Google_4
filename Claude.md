## Code Style & Standards

### General Principles

- Prefer editing existing files over creating new ones
- Avoid unnecessary comments; only add comments when the WHY is non-obvious
- Default to no comments for clear, self-documenting code
- Don't explain WHAT the code does - use well-named identifiers
- Avoid premature abstractions - three similar lines is better than an over-generalized helper

### Error Handling

- Don't add error handling for scenarios that can't happen
- Trust internal code and framework guarantees
- Only validate at system boundaries (user input, external APIs)

### Security

- Be careful to avoid common vulnerabilities: command injection, XSS, SQL injection, OWASP top 10
- Never generate or guess URLs unless confident they're for legitimate purposes
- Prefer secure defaults and be explicit about security-related code

## Testing & Verification

- For UI/frontend changes: start the dev server and test the feature in a browser
- Test both the golden path and edge cases
- Monitor for regressions in other features
- Type checking and tests verify correctness, not feature correctness

## File Operations

### Reading Files

- Use the Read tool for existing files
- For large files, read specific sections using offset/limit parameters
- Don't re-read a file after editing to verify changes

### Writing Files

- Create new files only when explicitly required
- Prefer using Edit tool for modifications to existing files
- Always read a file first before editing it with the Edit tool

## Documentation Standards

- Don't create documentation files (*.md) unless explicitly requested

## Handling Risky Actions

Before taking irreversible actions:
- Check with the user first, especially for:
  - Deleting files or branches
  - Force-pushing
  - Amending published commits
  - Removing dependencies
  - Modifying CI/CD pipelines

- For git operations: run `git status` before any command that could discard changes
- Stash or commit any in-progress work before destructive operations
- Only take risky actions when explicitly authorized

## Scheduled Tasks

When running as a scheduled task:
- No live user is watching - focus on actionable results
- Use PushNotification to surface findings that need attention
- Don't notify for routine progress or unchanged state
- Include <routine_summary> tags when notifying with the most important information first
